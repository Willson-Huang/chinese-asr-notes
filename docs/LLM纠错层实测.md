# 用 LLM 给 AI 字幕做纠错：两例实测

> **适用范围（先读这段再读数据）**
>
> 本方案是 **「不考虑时间链」的方案** —— 输入是把字幕 cue 按顺序拼接、**剥掉全部 `[hh:mm:ss]` 时间戳**后的连续语流，输出同样**不含任何时间戳**。
>
> 因此：
>
> - ✅ 适用于「我要一段**读得通、专名对**的全文」——做摘要、做检索、做二次加工、判断内容值不值得用。
> - ❌ **不能直接当素材包用**。本仓库的素材包约定「正文每行都要带 `[hh:mm:ss]` 前缀」（`tools/verify_pack.py` 会强制校验），本方案的输出进不了这个格式，**必须另做一步 cue 重新对齐**才谈得上接入流程。
> - ⚠️ 所以下面所有正确率数字，都是在「**放弃时间轴**」这个前提下测得的。如果需求是逐句引用、回跳音频时间点，请先补对齐，再按对齐后的结果重新评估。
>
> 另：两例的输入都来自 B站 AI 字幕（"中 → 英 → 中"回译产物，全篇零标点）。方法本身与平台无关，换成任何**有明显识别错误**的转写文本都适用。

---

## 0. 一句话结论

两条路线的收益结构完全不同，但**都成立**：

| 视频 | 内容类型 | 原文正确率 | LLM 纠正后 | 净提升 |
|---|---|---|---|---|
| BV1SgYT6sEzU（科技狐，10:41） | 泛科技 / 英文专名密集 | 30.4% | **93.9%** | **+63.5pp** |
| BV1dvKBzeEz3（老猫鱼不吃鱼，35:40） | 中文地名密集 | 85.0% | **100.0%** | **+15.0pp** |

关键判据（两例合起来才看得出）：

> **同一实体的正确写法是否在文内出现过，决定「外部上下文」是否必需。**
> 文内出现过 → 纯文本自洽即可收敛，给上下文几乎无增益（+0.3pp）；
> 文内一次都没出现过 → 必须带上下文，否则收益对折甚至方向性错误（+38.2pp）。

这条判据可以直接当决策规则用：**先看你的错误是"同实体多种写法并存"还是"全篇一致地错"，前者不必喂上下文，后者必须喂。**

## 1. 实验设计

### 1.1 被测对象

| 项 | 视频1 | 视频2 |
|---|---|---|
| BV号 | BV1SgYT6sEzU | BV1dvKBzeEz3 |
| 标题 | 飞书被拆、腾讯猛攻，阿里入局，AI 巨头在争什么？【科技狐】 | 发大水的肇庆居然当过古都？为什么又是大宋徽宗快乐之城？快递里的中国 广东 肇庆 |
| UP主 | 科技狐 | 老猫鱼不吃鱼 |
| 时长 | 10:41（636.9s 音频） | 35:40（2140s 音频） |
| cue 条数 | 333 | 966 |
| 剥离时间戳后正文字数 | 3,957 字 | 9,892 字 |
| 真值锚点表 | 29 个实体 | 86 个高置信 + 17 个歧义（分开计） |
| 官方人工 CC 字幕 | 无 | 无 |
| 是否有本地 ASR 可参照 | 有（Fun-ASR-Nano） | 无 |

两个视频的 AI 字幕都有共同缺陷：专名被回译成音近写法、**全篇零标点**、cue 是被切碎的光秃字流。333 / 966 条 cue 里，**没有一条以句末标点结尾**。

### 1.2 处理方式

字幕 cue 去时间戳 → 顺序拼接还原为连续语流 → 交 DeepSeek 纠正。
**不做任何时间轴相关处理**（这正是文首「适用范围」说的事）。

### 1.3 四组对照条件

| 代号 | 模型 | 外部上下文 | 输出形态 | 设计意图 |
|---|---|---|---|---|
| **A** | `deepseek-flash`（思考模式） | 带 | 全文重写 | 主方案 |
| **B** | `deepseek-flash` | **不带** | 全文重写 | 上下文消融，测上下文值多少 |
| **C** | `deepseek-flash` | 带 | 只出修正清单（JSON） | 可审计的部署形态 |
| **D** | `deepseek-chat`（非思考模式） | 带 | 全文重写 | 低成本 / 低延迟对照 |

对照基准 `RAW` = AI 字幕原文。

### 1.4 提示词骨架（两例共用）

```
【外部上下文】   标题 / UP主 / 简介 / 内容主题          （B 组删去本段）
【纠错要求】     说明缺陷类型：专名回译失真 / 同音字 / 全篇无标点
【硬性约束】     · 只纠错，不改写、不润色、不概括、不增删
                 · 口语重复、口头禅、病句、玩笑梗一律原样保留
                 · 同一实体全篇统一为同一写法
                 · 标点只补写，不得因断句改动字词
                 · 拿不准保留原样，绝对不要猜
                 · 只输出正文（C 组改为"只输出 JSON 修正条目"）
【字幕原文】     拼接后的语流
```

参数：`temperature=0`、`stream=false`、`max_tokens=32768~65536`。

### 1.5 真值表怎么建

不用第三方标注，用**「已知正确写法 + 实测错误变体」成对建表**：

```
正确写法 , [ 该实现在原文里出现的错误形态 ]
例（视频1）：WorkBuddy → [work body, work8里, 沃克巴黎, WORKBODY, work k8I, WORKBOY, ...]
例（视频2）：怀集      → [怀吉]
```

来源三路互证：① 视频自身上下文 ② 既有核对记录 ③ 外部公开资料。

**建表时必须先问一句：这个"错写"会不会在正常语境下合法出现？** 见第 4 节，两例都在这上面踩过坑。

### 1.6 指标定义

| 指标 | 定义 |
|---|---|
| 正确命中 | 正确写法在全文出现的次数之和 |
| 错误命中 | 已知错误变体在全文出现的次数之和 |
| **正确率** | 正确命中 ÷（正确命中 + 错误命中） |
| 全对实体 | 该实体全篇只出现正确写法、零错误变体 |
| 有错实体 | 该实体仍有 ≥1 次错误写法残留 |
| 内容丢失 | 与原文的最长连续删除片段长度 |
| 数字保真 | 原文数字锚点在各版本中是否变动 |
| 越界 | 把原本正确的内容改成错误 |

## 2. 结果

### 2.1 视频1 BV1SgYT6sEzU（英文专名密集，29 个实体）

| 版本 | 条件 | 正确命中 | 错误命中 | 正确率 | 全对实体 | 有错实体 |
|---|---|---|---|---|---|---|
| RAW | AI 字幕原文 | 28 | 64 | 30.4% | 5/29 | 24 |
| — | *本地 Fun-ASR-Nano（参照）* | *55* | *23* | *70.5%* | *8/29* | *17* |
| B | flash 无上下文 | 54 | 43 | 55.7% | 10/29 | 18 |
| D | chat + 上下文 | 79 | 18 | 81.4% | 15/29 | 13 |
| C | flash + 上下文 + 修正清单 | 87 | 6 | 93.5% | 21/29 | 5 |
| **A** | **flash + 上下文 + 全文重写** | **93** | **6** | **93.9%** | **22/29** | **5** |

原文即错、且**正确写法全篇一次都没出现**的代表：

| 实体 | 正确命中 | 错误命中 | 原文的错误写法 |
|---|---|---|---|
| WorkBuddy | 0 | 15 | work body / work8里 / 沃克巴黎 / WORKBODY / work k8I / WORKBOY / work巴的 …（共 9 种） |
| OpenClaw | 0 | 12 | open ko / open cloud / open cao / open club / open克洛 / open color / Open cw …（共 9 种） |
| ChatGPT | 0 | 3 | XJBT / 下GBT / Chat B |
| 陈宇森 | 0 | 1 | 陈雨生 |

- **A 组残留（2 处）**：陈宇森 仍作「陈雨生」；ChatGPT 仍作「XJBT」。
- **A 组额外修好、C 组没修的两处**：团队名「QTIM团队」→ **Qoder团队**（C 组误改成「Qwen团队」）；结尾乱码署名被重构。
- **A 组超过了本地 ASR**：93.9% vs Fun-ASR-Nano 的 70.5%。原因是 Nano 的短板（英文 token 粘连、音近替代）与 AI 字幕回译**同源**，而 LLM 有世界知识能补上两者都缺的那部分。

| | 视频1（英文专名） | 视频2（中文地名） |

## 3. 时间与 token 消耗

### 3.1 逐条件明细

计价基准：**DeepSeek V4-Flash 空闲时段** —— 输入缓存未命中 1.5 元/百万 token、输出 4.5 元/百万 token；
**推理 token 计入输出计费**。

|---|---|---|---|---|---|---|---|---|---|---|---|
| 视频1 | A | flash | 97.1 | 2,446 | 22,363 | 19,972 | **89.3%** | 2,391 | 10.7% | 0.1043 | 0.590 |
| 视频1 | B | flash | 20.0 | 2,303 | 4,470 | 2,433 | 54.4% | 2,037 | 45.6% | 0.0236 | 0.133 |
| 视频1 | C | flash | 121.0 | 2,431 | 29,868 | 28,337 | **94.9%** | 1,531 | 5.1% | 0.1381 | 0.780 |
| 视频1 | D | chat | 9.8 | 2,420 | 2,053 | 0 | 0% | 2,053 | 100% | 0.0129 | 0.073 |
| 视频2 | A | flash | 146.9 | 6,631 | 33,343 | 26,492 | **79.5%** | 6,851 | 20.5% | 0.1600 | 0.269 |
| 视频2 | B | flash | 168.3 | 6,380 | 38,847 | 31,869 | **82.0%** | 6,978 | 18.0% | 0.1844 | 0.310 |
| 视频2 | C | flash | 92.4 | 6,587 | 23,771 | 22,346 | **94.0%** | 1,425 | 6.0% | 0.1168 | 0.197 |
| 视频2 | D | chat | 29.8 | 6,605 | 6,082 | 0 | 0% | 6,082 | 100% | 0.0373 | 0.063 |

### 3.2 输出 token 里推理占比极高

**推理 token 占计费输出的 54%–95%；真正产出给你看的正文只占输出的 5%–21%。**
也就是说：**按输出付的钱里，八成到九成半花在"模型的思考过程"上，不在正文上。**

| 条件 | 视频1 推理占比 | 视频2 推理占比 | 说明 |
|---|---|---|---|
| A 全文重写 | 89.3% | 79.5% | 主方案，正文仅占 10.7% / 20.5% |
| B 无上下文 | 54.4% | 82.0% | 视频1 因输入短、任务简单，推理最省 |
| C 修正清单 | **94.9%** | **94.0%** | 推理最重：要在脑内先做完全文比对再压缩成条目 |
| D chat（非思考） | 0% | 0% | 无推理，但视频2 直接原样回显、等于不做 |

补充比值（推理 token ÷ 输入 token）：视频1 A = **8.2×**；视频2 A = **4.0×**。
即**输入越短，单位输入触发的推理越多**。

### 3.3 `max_tokens` 必须放大，否则返回空正文

首轮把 `max_tokens` 设为 8000，**三组全部返回空字符串且不报错**：

| 首轮调用 | 耗时(s) | 输入 tok | 输出 tok | 推理 tok | 正文 | finish_reason |
|---|---|---|---|---|---|---|
| A 全文重写 | 38.5 | 2,446 | 7,999 | 7,999（100%） | **0 字符** | `length` |
| B 无上下文 | 38.0 | 2,303 | 8,000 | 8,000（100%） | **0 字符** | `length` |
| C 修正清单 | 18.4 | 2,431 | 4,000 | 4,000（100%） | **0 字符** | `length` |

预算被推理 token 吃光，`content` 为空、`finish_reason=length`，**接口不返回任何错误**。

> 接入硬要求：`max_tokens ≥ 32768`；并加一条「正文为空即判失败」的检查。

| 口径 | 视频1（10.6 min） | 视频2（35.7 min） |
|---|---|---|
| 单条成本（A 组） | 0.104 元 | 0.160 元 |

## 4. 建真值表踩过的坑（影响数字可信度）

1. **「合法常用词」不能当错写变体**
   视频2 曾把「分开」列为封开的错写变体，但原文在讲封川 / 开建合并时「分开」是**合法动词**（"上边又把他们给分开了"），对所有版本假阳性。已剔除。
2. **地域梗 / 网络玩笑写法不算错**
   「吊州」是常州的地域梗（故意用法）、「胡建沙县」是"福建"的玩笑写法 —— 均从错写表移出。
3. **真值表自己也会有假阳性**
   视频1 曾把「AI 原生办公智能体」（无排版空格的正确写法）、「彼得·斯坦伯格」（带间隔号的正确写法）、「markdown」（大小写差异）、「open ai」（正确写法）、「CHATBOT」（该处指"聊天机器人 ChatBot"，本义正确）误列为错写，修正后重算。
4. **口径敏感性（必须披露）**
   视频1 含大量拉丁专名，变体之间存在**重叠与大小写差异**，同一份产出在不同计数规则下绝对值会浮动：

   | 口径 | 视频1 原文 | 视频1 纠正后（A） |
   |---|---|---|
   | 本报告采用（大小写敏感严格匹配 + 已剔除假阳性变体） | 30.4% | 93.9% |
   | 大小写不敏感计数 | 26.5% | 91.9% |
   | 全量变体未剔除假阳性 | 28.7% | 95.6% |

   **量级与结论方向在两例中均不变**；跨视频对比要按同一口径读，不要把某一次的绝对值当硬指标。

## 5. 采用建议

| 场景 | 建议 | 依据 |
|---|---|---|
| 英文专名 / 产品名密集（科技、AI 产品向） | **强烈推荐**。原文 30.4% 属不可用，纠正后 93.9% 已可用，且**高于本地 ASR 的 70.5%** | 视频1 |
| 中文地名 / 人名密集 | 推荐，但属**锦上添花**（原文 85% 本已能用，问题是专名不统一会漏检索） | 视频2 |
| 有人工 CC 字幕 | 不采用，人工字幕仍是最高基准 | — |
| **需要逐句引用 / 回跳时间点** | **本方案不适用**（无时间戳），必须先补 cue 对齐 | — |
| 内容不宜外发 | 需先裁决：本方案会把正文发往外部 API | — |

**三道闸门**

1. **输入**：始终带外部上下文（标题 / UP主 / 简介 / 主题）——它覆盖「全篇一致地错」那部分，而那部分最致命。
2. **输出**：A 出稿 + C 出清单**交叉核对**，分歧点人工裁决（A 曾出现"局部重解释"，C 曾出现 1 处误改）。
3. **校验**：数字锚点比对 + 长度比对（±20%）+「拿不准保留原样」写进提示词；`max_tokens ≥ 32768`，正文为空即判失败。

**模型与形态**

- 只用 `deepseek-flash`（思考模式）。`deepseek-chat` 在长文本上会原样回显、等于不做（视频2 实测）。
- **A（全文重写）**优于 **C（修正清单）**：视频1 93.9% vs 93.5%，视频2 100.0% vs 99.7%，且 A 多修好若干非目标错误；C 的价值在**可审计**（59–62 条可逐条核对的条目）。

## 7. 限制与未做

- **未做时间戳回填**（本方案的核心适用范围限制，见文首）。输出无 `[hh:mm:ss]`，与素材包格式不兼容；进入正式流程前必须补 cue 重新对齐。
- **未在批量场景验证**：并发限制、失败重试、token 累积成本均未测。
- **真值锚点表由人工建立**，非第三方标注，存在主观性；视频2 另设 17 项歧义表**单独归档不计分**，避免"用自己的推断给模型打分"。
- **视频1 的本地 ASR 参照只有一次**（Fun-ASR-Nano，无热词），未与 LLM 纠正做同条件复测。
- 本报告的部分结论属于**文案层面的定量**（专名写法正确率），不等于内容层面的语义保真度已达同等水平。
