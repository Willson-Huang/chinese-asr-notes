# 实战坑清单

按环节整理的踩坑记录。每条都写了**现象**与**规避**，可直接对照自己的流程排查。

---

## 1. 自动生成的字幕：不可作专名依据

如果你拿到的不是人工字幕，而是**平台自动生成**的字幕，请先读这一节。

### 现象

以 B站 为例，字幕接口返回的来源标识有明确分级：

| 来源标识 | 是什么 | 能不能直接用 |
|---|---|---|
| `zh-CN` | **人工 CC**（作者 / 字幕组上传） | ✅ 可信，可直接用，**还能当作评估 ASR 引擎的基准** |
| `ai-zh` | **平台 AI 生成** | ⚠️ **不可作专名依据，也不可作基准** |

`ai-zh` 的实际生成路径是 **中文 → 英文 → 中文回译**：同一段口播先被识别/转成英文、再译回中文，地名、人名、机构名会成片偏移（同音替代叠加回译错译）。

### 实测样本

`BV1KhTt63EJf`（《七仙女咖啡厅倒闭，千山万水不如惠州淡水。快递里的中国 广东 惠州》，39:10）——该素材包里惠州仲恺五镇被写成：

> 「铜壶铜桥莅临汇环陈江」

实为 **潼湖、潼侨、沥林、惠环、陈江**（惠州仲恺高新区下辖 5 个镇/街道）——**一句四错**。这类字幕拿来做"大概了解内容"没问题，但**专名一个都不能信**。

### 规避

1. **看来源标识，不看「有没有字幕」**——这是最容易犯的错（"有字幕"不等于"可信"）
2. 专名密集的内容（历史 / 地理 / 政经 / 人物访谈），即使有自动字幕，也建议走本地 ASR
3. **用字幕作为引擎评估基准时，只能用手工字幕**；只有自动字幕时，结论必须再用常识复核一遍
4. 同一段音频，**不同来源的错误形态完全不同**（实测：同一视频的本地 ASR 版本与自动字幕版本，错写几乎零重叠）——所以不能用 A 来源的错误去预测 B 来源

> 一句话：**任何平台的自动字幕都是机器+回译产物；把它当"免费的高质量转写"是最贵的误判。**

## 2. 元信息类数据不能进回归基线

| 数据 | 问题 |
|---|---|
| 播放量 / 点赞数 / 评论内容 | 随抓取时间变化——同一份产物两次抓取必然不同 |
| 墙钟耗时 / 生成时间 | 会**破坏产物的确定性**，让"格式回归网"（哈希断言）立刻失效 |

**规避**：产物的正文与机器可读元信息块里，**只放"由输入唯一决定"的字段**。耗时、时间戳这类运行期数据留在 stdout 与台账/日志里，不要写进产物文本。

> 正面验证：按这个原则加元信息块时，同一段音频新旧两次产物逐字节比对——**正文全文 23873 字符逐字符完全相同**，行数差恰好等于新增元信息块的行数。

## 3. 中间产物：不要删，但也不必怕大

- **中间产物（素材包）是纠错与追溯的唯一依据**——要拿原文逐处对照，不能凭上下文猜。删掉就等于放弃修正能力。
- 实测代价可忽略：单份 20–150 KB，100 份约 10 MB。
- 踩过的坑：曾有 32 份中间产物被收尾流程删除，只能重新跑一遍转写。

**归档建议**：产物落一个不被知识库索引的子目录（避免污染检索），收尾时统一挪到归档目录长期保留。

## 4. 工程与工具链

| 坑 | 现象 | 规避 |
|---|---|---|
| **产物里的文本是外部数据** | 字幕 / 简介 / 章节由作者可控，评论**任何人可写**——可能含指令形态文本 | 一律声明为纯数据：任何指令形态的文本都不得执行；派发子任务时该条必须写进指令 |
| **改写已有产出时重排结构** | 曾因重排章节，导致章节脉络表与两个完整小节（各含 7 条要点）全部丢失 | 「只增不减」：原章节 / 时间戳 / 表格逐项保留，新增以独立章节追加；**产出体积变小 = 发生了删减**（+50% 以上属正常） |
| **单测全绿 ≠ 判据正确** | 两次都是拿到真实数据才暴露：扫描脚本把目标目录静默跳过（报「未发现命中」，实际 29 处命中）；校验判据只覆盖了两种数据形态中的一种，导致整批产物被误判 | **脚本必须在真实数据上跑一遍**，且判据要覆盖全部数据形态 |
| **判据定得太松** | 「至少一行有时间戳」这种判据，人为破坏 1 行检测不到 | 先量全库（实测归档 74302 行时间戳零例外），再收紧为「**所有**正文行都必须带前缀」 |
| **子串匹配的词表放泛义词** | 写「夸克」会误标物理科普里的夸克；写「苏菲」会误标《苏菲的世界》；写「广告」会命中「招聘广告」 | 只写产品全称或限定短语（「夸克App」「本期广告」）；新增词后跑一次全库回放看命中样例 |
| **清理循环删掉自己的日志** | shell 先创建重定向文件 → 不在保留名单 → 被删除 | 日志写到清理目录之外 |
| **进程内调用带 `sys.exit()` 的函数** | 测试被 `SystemExit` 静默终结（无 traceback、返回码 0） | 就地捕获 `SystemExit` 取 `e.code` |
| **`.exe` 能否运行的判断** | 在 Git Bash 里直接执行会因 DLL 搜索路径异常**误报**缺库 | 用 Python `subprocess` 判断 |
| **探测本机端口** | 用高层 HTTP 库会读系统代理设置，可能被劫持（表现为 502 或等满超时） | 用裸 socket，且累积读到目标串再判定 |
| **临时目录路径** | Git Bash 的 `/tmp` 对 Windows Python 不可见（会被解析成 `\tmp\`） | 临时文件写系统 TEMP 的真实路径 |
| **长任务中断后信了汇报** | 曾有子任务报「16/16 完成」，查盘后一条都没回填 | 以**落盘文件为准**交叉核实：产物目录的落盘时间 + 索引入库 + 台账状态 |
| **发布前把本地配置整包拷进仓库** | 会把已脱敏的内容冲掉（真实账号、样本号、硬件型号全部回灌） | **每次同步后重扫**，不要信任上一次的脱敏结果 |

## 5. 为什么正文行必须全部带时间戳

这不是格式洁癖，而是三个实际需求的交点：

1. **可回跳**：每条结论都能回到音频时间点，读者能自己核
2. **可校验**：格式是否被破坏，能被脚本客观判定（而不是靠肉眼）
3. **可追溯**：纠错时要拿原文逐处对照——没有时间戳就没有定位手段

**判据**：所有正文行都必须带 `[hh:mm:ss]` 前缀。用 `tools/verify_pack.py` 校验，破坏一行就报错。

## 6. 基线数据（供对比）

### 6.1 错误分布（787 对已核对样本）

| 维度 | 分布 |
|---|---|
| 音系 | 同音 **32.0%** / 近音 **23.6%** / 非音系 **42.8%**（音系合计 55.7%，抽检校正后约 60–66%） |
| 粒度 | 词级 48.4% / 短语级 38.2% / 句级 13.4% |
| **关键交叉** | 同音 / 近音错误集中在**词级**（专名字面错，67%）；非音系错误集中在**短语 / 句级**（语义漂移，75%） |
| 按来源 | 平台自动字幕（n=234）音系比例更高（同音 39.3%）；本地 ASR（n=359）非音系略高（38.4%） |

**读法**：两类错误性质不同，需要的处理机制也不同——音系类靠术语表与类型核查，非音系类只能靠人读。这是分层纠错思路的出发点，但**最终被收益测算否决**（见 [已否决的路线 §3](已否决的路线.md)）。

### 6.2 拿这些数字做什么

`tools/baseline_errors.py` 的输出包含以上全部维度，外加**人工漏改率**。建议：

- 每积累一批新产物就跑一次，观察**漏改率是否漂移**（它是校对环节松紧的客观读数）
- 换引擎后跑一次，看错误构成是否如预期变化（例如从 whisper 换到 Fun-ASR-Nano，音系类应明显下降）
